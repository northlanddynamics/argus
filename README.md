# Argus

Collaborative security case management for in-house teams. Vocabulary: `GLOSSARY.md`. Decisions: `docs/adr/`.

## Layout

- `apps/api`: Hono API on Bun, Better Auth at `/api/auth/*`, Postgres via Drizzle. In production it also serves the built SPA.
  - `src/crowdstrike/`: the Falcon API adapter and the `worker` process's Event Streams ingest (ADR 0002).
  - `src/mimecast/`: the Mimecast API 2.0 adapter and the `worker`'s credential health checks (ADR 0007).
  - `src/umbrella/`: the Cisco Umbrella API v2 adapter, the `worker`'s credential health checks and domain checks against destination lists (ADR 0014).
  - `src/routes/`: HTTP only: validate, call a module, map its errors to status codes.
  - `src/cases/`, `src/tasks/`, `src/case-roles/`, `src/discussion/`, `src/timeline/`, `src/evidence/`, `src/observables/`, `src/case-links/`, `src/tags/`, `src/alerts/`, `src/internal/`, `src/integrations/`, `src/notifications/`, `src/teams/`, `src/case-reports/`, `src/search/`, `src/members/`, `src/invitations/`, `src/organizations/`, `src/sso/`: one module per area of the domain, built in `src/modules.ts`; the only code that touches the database (ADR 0006).
- `apps/web`: Vite + React SPA (shadcn/ui, TanStack Router, TanStack Query), typed against the API through Hono RPC (`api/client`).

## Develop

```sh
bun install
cp .env.example .env               # then edit
bun --cwd apps/api db:migrate
OPERATOR_PASSWORD=... bun --cwd apps/api operator:create ops@example.com "Ops"
bun run dev:api                    # :3000
bun run dev:web                    # :5173, proxies /api to :3000
bun apps/api/src/worker.ts         # the worker: CrowdStrike Event Streams
```

## Checks

```sh
bun run lint
bun run typecheck
bun run test        # API tests against a real Postgres (TEST_DATABASE_URL, an admin connection)
bun run test:e2e    # builds the SPA, then a Playwright smoke test with the pre-installed Chromium
```

Members who sign in with a password must use TOTP: until they enroll, their session reaches only the enrollment endpoints (`apps/api/src/auth/totp-enrollment.ts`). Passkeys use `BASE_URL` as their origin and its hostname as the relying party ID, so set it to the public origin.

SAML SSO (`apps/api/src/sso/`): an Admin enables it for their Organization in Settings · Single sign-on (`PUT /api/sso`) with the email domain it covers and the identity provider (its metadata XML, or its entity ID, sign-in URL and signing certificate), changes it, and disables it (`DELETE /api/sso`); each change is recorded in the Organization Audit Log. Settings shows what to give the identity provider: Argus's entity ID (`BASE_URL/api/auth/sso/saml2/sp/metadata?providerId=…`) and ACS URL. Better Auth's `sso` plugin runs the sign-in: "Sign in with SSO" sends the person to the identity provider for their email's domain, and Argus accepts only signed assertions answering a sign-in it started. Each verified identity is matched by email to a Member of that Organization; failing that, someone with a pending invitation joins with the invited role, and, if the Organization provisions Analysts, someone at its domain joins as an Analyst (recorded as `member.joined`). Anyone else is sent back to sign-in with the reason. Sessions started with SSO need no TOTP: the identity provider is the second factor. Disabling SSO ends them. The plugin's own endpoints for managing connections are closed.

Evidence (`apps/api/src/evidence/`) is stored in an S3-compatible bucket through Bun's S3 client: set `S3_BUCKET` and its credentials (`S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`; MinIO works locally). Without `S3_BUCKET` the app runs but Evidence uploads and downloads fail. Files are fingerprinted with SHA-256 as they stream in, written once under a fresh key and never overwritten or deleted; turn on S3 Object Lock for a bucket that can't be altered from outside Argus either. Bytes reach browsers only through the API, which records every view and download in the Case Audit Log first. `EVIDENCE_MAX_BYTES` caps a file (default 64 GiB).

CrowdStrike (ADR 0002): Admins add an Integration with Falcon API credentials (an API client with Event Streams read access), sealed at rest with AES-256-GCM under `CREDENTIALS_SECRET` (default `BETTER_AUTH_SECRET`). The `worker` process (`apps/api/src/worker.ts`, same image) claims each Integration's stream with a Postgres advisory lock, so exactly one worker reads it however many run; another takes over when it stops. It turns `EppDetectionSummaryEvent`, `IdpDetectionSummaryEvent` and `MobileDetectionSummaryEvent` into Alerts keyed by `CompositeId`, stores each event's offset with its result and resumes after it on reconnect, refreshes the stream session before Falcon's 30-minute expiry, and records a gap Falcon can no longer replay in the Organization Audit Log without backfilling it. Each Integration is read only unless an Admin turns on its write-back (`PUT /api/integrations/:id/write-back`, or the switch in Settings · Integrations); the change is recorded in the Organization Audit Log. With write-back on, attaching an Alert sets it `in_progress` in Falcon with a comment linking to the Case, dismissing one sets it `closed` with the Dismissal Reason as a comment, closing a Case closes its attached Alerts with the Resolution as a comment, and changing a Case's Assignee assigns its Alerts to the Falcon user with the same login email (skipped when there is none). Each change is queued in the `falcon_write_backs` outbox in the transaction that made it; the worker sends them (`crowdstrike/write-back.ts`), one Alert's changes in order, claiming batches with `FOR UPDATE SKIP LOCKED` so each is sent by one worker, retrying failures with backoff (30 s doubling to an hour, given up after 10), and cancelling any still unsent when write-back is turned off. Settings · Integrations shows the counts.

Alerts (`apps/api/src/alerts/`): Members open one Case from selected Alerts (its Severity defaults to the highest of theirs), attach them to a Case, move or detach them, and dismiss them with a Dismissal Reason. Every action names each Alert with the version the Member saw; bulk actions refuse, one by one, Alerts that changed since, and apply the rest. Attaching, moving and detaching are recorded in both Cases' Audit Logs, dismissals in the Organization Audit Log, and the database keeps an Alert on at most one Case. Each detection's Observables (hashes, remote IPs, DNS lookups) and Assets (hosts, accounts) are extracted as it arrives (`crowdstrike/indicators.ts`, fixtures in `crowdstrike/fixtures/`) and held once per Organization; attaching the Alert links them to the Case as "Alert (auto)", and detaching it unlinks them again unless they were added by hand or another Alert on the Case names them too.

Correlation (ADR 0015) suggests which Cases an Alert belongs with, and which New Alerts belong with a Case (its Related Alerts), by the Important Observables and the Assets they share, neither on the Ignored list. Any Member marks an Observable Important for the whole Organization, or unmarks it, from its right-click menu, a Case's row menu, the Enrichment panel or its page (`PUT`/`DELETE /api/observables/:id/important`, or `POST /api/observables/important` with `{ type, value, important }` for one the Organization may not hold yet); Members list them with `GET /api/important-observables`. Each mark is kept in `important_observables` (migration 0053) and recorded in the Organization Audit Log. Observables nobody has marked never relate an Alert to a Case. Guests can't mark them and aren't told.

Observable and Asset pages (`apps/api/src/observables/`, `GET /api/observables/:id`, `GET /api/assets/:id`, `/observables/:id` and `/assets/:id` in the SPA): each Observable and Asset has a page showing its value (Observables defanged), first and last seen (from when it was linked to the Cases and when the Alerts naming it were raised, among those the viewer can see), every linked Case the viewer can see with its Status, Severity and Assignee, and every Alert naming it in any Alert Status with its Case where the viewer can see it. Restricted Cases the viewer can't see, and their Alerts, are neither shown nor counted. Guests open only items on a Case they've been granted, see only those Cases and no Alerts; anything else is not found. Search results, each value on a Case's Observables & Assets (whose breadcrumb then leads back to that Case) and an Alert's extracted indicators link there, while "seen in" links each other Case itself, and any Case or Alert signal refreshes it. A host's page also lists, for Members, each Falcon device (`aid`) recorded on it per CrowdStrike Integration (ADR 0009), with a link to the device in that Integration's console: detections record their sensor's `aid` against the host they name as they arrive (`asset_falcon_devices`, once per host, Integration and device), the hostname staying the match key, and a host with several devices for one Integration is marked ambiguous there. The console link is unverified against a live tenant. Each device also shows its Enrichment, what Falcon's Hosts API reports about it now (`crowdstrike/host-enrichment.ts`): platform and OS, sensor version and status, first and last seen, IPs and MAC, domain, OU and site, hardware, last logged-on user, host groups, Falcon tags and containment status, as of when it was fetched, an ambiguous host's devices side by side. Only the latest snapshot of each device is kept (`falcon_host_snapshots`). A Member opening the page marks snapshots older than 15 minutes due, and Refresh (`POST /api/assets/:id/enrichment`) marks them all; the worker fetches due ones and a signal refreshes the page. A device Falcon doesn't know shows "Not found in Falcon"; a failed fetch keeps the last snapshot and says why. Enrichment needs no Admin setting: when the API client lacks Hosts: Read, the Integration's health says host enrichment is unavailable and nothing else is affected. A host with no device recorded for a CrowdStrike Integration (added by hand, or named only by detections without an `aid`) is first looked up there by hostname (`falcon_host_lookups`), due and done by the worker the same way: one match records that device, several are all recorded and mark the host ambiguous, and no match shows "Not found in Falcon" and is looked up again on the next fetch. Once a device is recorded, its `aid` is used and not the hostname. Guests see none of it on the host's page. A Case's Assets (`GET /api/cases/:number/assets`) carry the key Enrichment facts of each linked host, `falcon`: OS, last seen and containment of each device, as of when they were fetched, or how looking it up by hostname went. Opening the Case asks again for anything older than 15 minutes, as opening the host's page does, and the fetch signals every Case the host is linked to. Guests see these facts too, but never a console link, the Integration, an error or its health. The Hosts API calls are unverified against a live tenant. An account's page likewise shows, for Members, the Falcon Identity Protection identities it resolves to per CrowdStrike Integration (`crowdstrike/identity-enrichment.ts`, ADR 0009): an account with none recorded is looked up by name (`falcon_identity_lookups`), by UPN or email when it has an `@`, by domain and SAM name for `DOMAIN\user` (the domain as its DNS or NetBIOS name), and by SAM name alone otherwise, which may match several identities and mark the account ambiguous; every match is recorded (`asset_falcon_identities`) and its entity ID used from then on. Each identity shows its Enrichment (`falcon_identity_snapshots`): risk score, severity and risk factors; enabled, locked out, stale, privileged (with the privileged groups) and watched; when the password was last set and whether it never expires; last activity, email, department and title, domain and OU; and the endpoints associated with it, listed by hostname and never linked to the Case. Freshness, Refresh, "Not found in Falcon" and failures work as for hosts. Without the Identity Protection Entities: Read scope or an Identity Protection subscription, the Integration's health says identity enrichment is unavailable and nothing else is affected. The Identity Protection GraphQL queries are unverified against a live tenant.

IPinfo (ADR 0010): an Admin adds the Organization's one IPinfo Integration with an API token (`POST /api/integrations` with `provider: "ipinfo"` and `token`, or "+ Add IPinfo Integration" in Settings · Integrations), sealed like the others; it has no Alert stream, write-back or Response Actions, and its token is rotated with `PUT /api/integrations/:id/credentials` and `{ token }`. Any Member looks up any IP (`GET /api/ip-lookups?ip=…`, defanged or not; `POST /api/ip-lookups/refresh` with `{ ip }` always asks IPinfo) through IPinfo's Core API (`ipinfo/ipinfo-http.ts`, unverified against a live token): reverse DNS, location, the announcing AS and its type, and the anonymous, hosting, anycast, mobile and satellite flags. The `web` process asks IPinfo while the Member waits and caches each answer in `ip_lookups` (migration 0047), one per Integration and address, served for 7 days; a failed lookup keeps the last answer, says why, sets the Integration's health and isn't retried for a minute. Private, loopback, link-local, CGNAT, documentation, multicast and other reserved addresses are never sent (`ipinfo/ipinfo.ts`). The worker checks the token once when it is added, rotated or resumed (`ipinfo/health.ts`). In the SPA, hovering or focusing an IP opens what IPinfo says about it (`components/ip-details.tsx`, wireframes in `docs/wireframes/ip-context-popup.md`): on a Case's Observables, Alerts' extracted indicators, Bulk Lookup, Response Actions and a host's Falcon IPs; an IP Observable's page shows it as a card. Guests get neither. Tests swap in `fakeIpinfo()` (`t.ipinfo`: `details`, `bogons`, `refused`, `quotaExceeded`, `unreachable`, and every lookup in `lookups`).

VirusTotal (ADR 0011): each Member sets their own VirusTotal API key in Your settings (`/account` in the SPA, `GET`/`PUT`/`DELETE /api/virustotal-key` with `{ apiKey }`), sealed like Integration credentials, checked by looking up the EICAR test file before it is saved, shown back only by its last four characters, and gone with their membership. Any Member looks up any MD5, SHA-1 or SHA-256 (`GET /api/hash-lookups?hash=…`; `POST /api/hash-lookups/refresh` with `{ hash }` always asks) through VirusTotal's v3 file API (`virustotal/virustotal-http.ts`, unverified against a live key): detections by engine, threat label and categories, file type, size and names, signature, tags, submission and analysis times and community votes. The `web` process asks VirusTotal with the Member's own key while they wait and caches each answer for the Organization in `hash_lookups` (migration 0048) under each of the file's hashes: reports for a day, "never seen" for an hour. Members without a key read the cache and can't refresh. A failed lookup keeps the cached report, says why, records it on the key (`virustotal_keys`), and that key isn't tried again for a minute (`virustotal/hash-lookups.ts`). In the SPA, hovering or focusing a hash opens what VirusTotal says about it (`components/hash-details.tsx`, wireframes in `docs/wireframes/hash-context-popup.md`): on a Case's Observables, Alerts' extracted indicators, Bulk Lookup, Response Actions and Evidence fingerprints; a hash Observable's page shows it as a card. Guests get neither. Tests swap in `fakeVirustotal()` (`t.virustotal`: `files`, `unknown`, `refused`, `exhausted`, `unreachable`, and every lookup in `lookups`).

Domains, email addresses and URLs (ADR 0012) are looked up the same way, with the same key, cache rules and key failures (`virustotal/domain-url-lookups.ts`, `virustotal/member-keys.ts`): `GET /api/domain-lookups?domain=…` (a domain, or an email address, which is looked up by its domain alone) and `GET /api/url-lookups?url=…`, defanged or not, each with `POST …/refresh`. Answers are cached for the Organization in `virustotal_lookups` (migration 0049). A domain's report gives the engines' verdict, vendor categories, registration date and registrar, DNS records, its HTTPS certificate and popularity ranks, and the lookup says whether it was registered in the last 30 days (`newlyRegistered`); a URL's gives the verdict, page title, where it ends up after redirects, the HTTP status, categories and threat names. URLs are only looked up, never submitted for scanning. Names only meaningful inside a network (`.local`, `.internal`, `.corp`, …), URLs on reserved addresses and URLs carrying a username or password are never sent (`state: "withheld"`, with the reason). In the SPA, hovering or focusing a domain, email address or URL opens its popup (`components/domain-details.tsx`, `components/url-details.tsx`, sharing `components/virustotal-parts.tsx` with hashes; wireframes in `docs/wireframes/domain-url-context-popup.md`), and its Observable's page shows it as a card; the Observable menu opens a domain (or an address's domain) on VirusTotal. The fake records these in `t.virustotal.domainLookups` and `urlLookups`, says what `domains` and `urls` hold, and treats anything in `unknown` as never seen.

Internal items (`apps/api/src/internal/`): Members mark Tasks, Discussion messages, Timeline Entries, Evidence, attached Alerts and Response Actions Internal, and an Asset's link to a Case (`{ kind: "asset", id: <Asset id> }`, migration 0041), which hides the Asset and its Enrichment from that Case's Guests, its page and search included, or show them to Guests again, each change in the Case Audit Log. Attaching an Alert makes it Internal. The access policy (`visibleItems`, `canSeeItem`) leaves Internal items out of every Guest read, including an entry's citations of Internal Tasks, and signals about Internal items alone (`membersOnly`) never reach Guests' sockets. Guests post in the Discussion, own and complete Tasks and add Evidence, but never on Internal items: an Internal item can't mention a Guest or be owned by one. Evidence stays unalterable apart from its marking (migration 0019).

Case Reports (`apps/api/src/case-reports/`): anyone who can see a Case exports it (`GET /api/cases/:number/report?variant=complete|guest_safe&format=pdf|markdown`, or Export on the Case page) with its Case Summary, Timeline, Tasks, Observables, Assets and the Evidence list with SHA-256 fingerprints. The complete variant marks Internal items; the Guest-safe one is read through the item modules the way the Case's Guests read it (`readsAs: "guests"` in the access policy), so it leaves out every Internal item, Audit Log Promotions, other Cases and Alerts. Guests export only the Guest-safe one. Every export is recorded in the Case Audit Log (`case.report_exported`). Both formats come from one outline (`outline.ts`); Markdown escapes everything taken from the Case, and PDFs are A4 set in DejaVu Sans (the `dejavu-fonts-ttf` package), embedded and subset so any character prints.

Action Center (`apps/api/src/action-center/`, ADR 0016, `/actions` in the SPA): Members see every action Argus can take on an Observable, per Integration, and whether each can run now (`GET /api/action-center`), and run one on the values in any pasted text (`POST /api/action-center/run` with `{ action, text, integrationIds?, caseNumber?, reason?, internal?, confirmIgnored? }`). With a Case, each value is linked to it first and the action is taken from it. Without one, a Response Action needs a `reason`, which the tool is sent in place of the Case's reference; it is recorded in the Organization Audit Log (category `response-actions`) and can be retried, removed or dismissed from the Action Log (`POST /api/action-log/:id/retry|remove|dismiss`) until it is linked to a Case (`POST /api/action-log/:id/link` with `{ caseNumber }`), which moves it there for good. Contain host and Lift containment link the host to a chosen Case and open its confirmation. The Action Log (`GET /api/action-log?link=&group=&by=&before=`, `/actions/log`, table `action_log`, migration 0054) records every Response Action wherever taken, every Important and Ignored mark wherever made, and every lookup run from the Action Center, with its value, Integration, Case, who ran it, from where and how it went; rows on Cases the reader can't see are left out. Each change sends an `actions` signal to Members' sockets.

Global search (`apps/api/src/search/`): the search field in every page's header (or `/`, or ⌘K / Ctrl+K) opens a palette that searches as you type and shows the best five results across Cases, Alerts, Observables and Assets, with toggles to narrow it to some kinds; Enter opens the highlighted result, and "See all results" opens `/search?q=…&kinds=…&page=…`, one list of every result best first, 20 to a page, with the same rows and toggles and a count for each kind. `GET /api/search?q=…&kinds=cases,alerts&page=2&pageSize=20` ranks Cases (by title and Case Summary, or by reference, "C-12", ranked first), Alerts (by title, Falcon id, host, user and description), Observables and Assets (by value) on one scale in a single query, and returns that page of `hits` (each with its `kind`, `rank` and `item`), the `total` for the kinds asked for and the `counts` for every kind (page size up to 50). The query reads as a web search: words, "quoted phrases", `or` and `-excluded`; each word also matches as the start of a longer one ("invo" finds invoice-portal.biz), whole words ranking higher, and the words inside an Observable's or Asset's value count ("invoice portal" finds invoice-portal.biz). Observables and Assets are also found as analysts paste them (`search/indicators.ts`), defanged or not: an exact value first; a domain's subdomains, URLs and email addresses; the URLs a URL starts; an IPv4 range by its first two or three whole parts ("185.220"); and the hashes that start with 8 or more hex characters, or with 4 to 7 that mix digits and letters, as the Observables tab shortens them ("e3b0"). Results say which Observables and Assets are on the Ignored list, never to Guests. Postgres full-text search runs over a generated `search` column on each table (the `simple` configuration, so hashes, IPs and host names stay whole), with GIN indexes (migration 0028). Results go through the access policy: Restricted Cases appear only to those who can see them, and so do Observables and Assets linked only to them; Members search the whole Alert queue but see an Alert's Case only if they can see it; Guests find only their Cases, what is linked to them, and the Alerts on them that aren't Internal.

Live updates (ADR 0005): each signed-in tab holds one WebSocket at `/api/live` (`apps/api/src/realtime/`). Changes publish a signal with `pg_notify` in the same transaction; every process listens and forwards it only to sockets whose Member can see the Case, and the SPA (`apps/web/src/lib/live.ts`) invalidates the matching queries. Presence is kept in `case_viewers`, refreshed by each process's heartbeat.

Notifications (`apps/api/src/notifications/`): people are notified in-app and by email when they are made a Case's Assignee or a Task's owner, when they are @mentioned, when a Guest is added to a Case they are Assignee of, when a Case they take part in (as Assignee, Case Role holder or Guest) is raised to Critical, and when a Task they own falls overdue (once per due date; the worker checks). Nobody is notified of their own action, nor about a Case or item they can't see; the access policy is asked again whenever notifications are read, so ones about Cases or items since hidden from their recipient drop out. Each recipient marks theirs read (`/api/notifications`). A new notification signals its recipient's sockets, and the SPA's bell refetches and toasts it. Emails are queued in the same row in the transaction that made the change, sent once it commits, and retried by the worker (up to 5 times).

Teams channel (`apps/api/src/teams/`): an Admin sets the Organization's Teams incoming webhook in Settings · Integrations (`PUT /api/teams-channel`; a legacy connector URL on `*.webhook.office.com` or a Teams Workflows URL on `*.logic.azure.com` or `*.api.powerplatform.com`, HTTPS only), can send a test post to it, and can remove it; each change is recorded in the Organization Audit Log. The URL is sealed at rest like Integration credentials and never sent back; Admins see its host and last four characters. While it is set, a new Critical Case, a Case whose Severity is raised to Critical, and a Case opened from Alerts (at any Severity, with how many) are posted to the channel as an Adaptive Card linking to the Case. Posts are queued in `teams_posts` in the transaction that made the change, sent once it commits, and retried by the worker with backoff (30 s doubling, up to 5 attempts); they go to whichever webhook is set when sent, and are dropped if it is removed. Each is written from the Case as it is when sent: a Restricted Case's post says only what happened, with a link to the Case and none of its details.

Mimecast (ADR 0007): Admins add a Mimecast Integration with an API 2.0 application's client ID and secret (`POST /api/integrations` with `provider: "mimecast"`, or "+ Add Mimecast Integration" in Settings · Integrations), sealed like Falcon's. It has no cloud, no Alert stream and no write-back; it only takes Response Actions, once an Admin turns them on. The worker (`mimecast/health.ts`) signs in with its credentials when it is added, rotated or resumed and every 15 minutes: accepted is Connected, refused is Error with Mimecast's reason, unreachable is Reconnecting until it is checked again a minute later. From a Case, a Member blocks an email Observable's address (`action: "block_sender"`) or its domain (`"block_domain"`) through an Organization-wide Blocked Senders policy entry described `C-<n>: <title>` with a link to the Case; blocking a domain links the domain Observable to the Case by hand first if it isn't linked yet, and that Observable is what the Response Action is on. Anything but an email address is refused alone and skipped among others. Blocks go through the same outbox, "already present" rules and removal as Falcon IOCs (`response-actions/sender.ts`). The HTTP adapter (`mimecast/mimecast-http.ts`) is unverified against a live account.

Cisco Umbrella (ADR 0014): Admins add a Cisco Umbrella Integration with an Umbrella API key and secret whose scope includes Policies · Destination Lists, read and write (`POST /api/integrations` with `provider: "umbrella"`, or "+ Add Cisco Umbrella Integration" in Settings · Integrations), sealed like the others. It has no cloud, no Alert stream and no write-back; the worker checks its key as for Mimecast (`umbrella/health.ts`). An Admin chooses the destination list it adds domains to from Umbrella's lists (`GET /api/integrations/:id/destination-lists`, `PUT /api/integrations/:id/destination-list` with `{ destinationListId }`); until then it isn't offered on Cases. From a Case, a Member adds a domain Observable to that list (`action: "add_to_destination_list"`) with a comment `C-<n>: <title> <link>`; anything but a domain is refused alone and skipped among others, and the Response Action records the list it went to, so removal reaches that list whatever the Integration adds to now. It goes through the same outbox, "already present" rules and removal as Falcon IOCs. Any Member can check which destination lists hold a domain, or a domain above it (`GET /api/umbrella-checks?domain=…`, an email address checked by its domain; `POST /api/umbrella-checks/refresh` with `{ domain }` always reads the lists): the `web` process reads every list and matches in Argus, so the domain itself is never sent, and keeps what it read for five minutes (`umbrella/domain-checks.ts`). The Enrichment panel and a domain or email Observable's page show it under "Cisco Umbrella". The HTTP adapter (`umbrella/umbrella-http.ts`) is unverified against a live account. Tests use `fakeUmbrella()` (`t.umbrella`: `account(key).list(...)`, `hold(...)`, `added`, `removed`, `reads`, `refuse`, `unreachable`, `failNextCalls`), for `createResponseActionSender(t.deps, { umbrella: t.umbrella.connect })` and `createUmbrellaHealthChecker(t.deps, { connect: t.umbrella.connect })`.

Tests build the API in-process (`apps/api/src/test/harness.ts`) with a fresh database cloned from a migrated template, a fake clock, a captured mail outbox, captured Teams posts (`t.teams.posts`, `t.teams.failNext(n)`) and in-memory Evidence storage (`t.evidenceObjects`), and drive it over HTTP with the Hono RPC client and the Better Auth client. `t.acceptInvite(email, password, name)` accepts the latest invite sent to `email` and gives a fully signed-in, TOTP-enrolled Member; `t.totpCode(secret)` plays the authenticator app. `fakeIdp()` (`apps/api/src/test/fake-idp.ts`) is a SAML identity provider with a fixture signing key: configure Argus with its `metadataXml` (or `entityId`, `ssoUrl`, `certificate`), and `idp.signIn(t.session(), { email, name })` plays a person signing in through it. `t.connect(member)` opens that Member's live socket and collects what it receives; `t.anotherInstance()` starts a second server process on the same database. `fakeFalcon()` (`apps/api/src/test/fake-falcon.ts`) is a Falcon tenant's Event Stream that tests emit events into, drop and age out, for workers made with `createStreamWorker(t.deps, { connect: falcon.connect, workerId })` and driven by `worker.tick()`; `createNotificationWorker(t.deps).tick()` finds overdue Tasks and sends any notification emails still queued; `createTeamsSender(t.deps).tick()` sends Teams posts that are due. Its tenants also record each Alerts API patch (`tenant.patches`), hold Falcon users by email (`tenant.users`) and can fail writes (`failNextWrites`, `refuseWrites`), for write-back senders made with `createWriteBackSender(t.deps, { connect: falcon.connect })`. `fakeMimecast()` (`apps/api/src/test/fake-mimecast.ts`) holds a Blocked Senders list per API application (`account.blocked`, `created`, `deleted`, `hold(...)`) and can refuse its credentials (`refuse`), be unreachable (`unreachable`) or fail calls (`failNextCalls`), for `createResponseActionSender(t.deps, { connect: falcon.connect, mimecast: mimecast.connect })` and `createMimecastHealthChecker(t.deps, { connect: mimecast.connect })`.

## Generated code

- Better Auth schema: `bun --cwd apps/api auth:generate` (Better Auth CLI), then `bun --cwd apps/api db:generate` for the migration. Never hand-edit `apps/api/src/db/auth-schema.ts`.
- shadcn/ui components: `bunx shadcn@latest add <component>` in `apps/web`. Never copy them by hand.

## Production

`docker build .` produces one image that serves the API and the SPA (`bun apps/api/src/server.ts`), applying migrations on start. Run the same image as `bun apps/api/src/worker.ts` for the `worker` role; `WORKER_ID` names it (default host and pid).
